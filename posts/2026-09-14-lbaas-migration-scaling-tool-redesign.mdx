# Designing a maintenance-scaling tool talked me into three different architectures before I gave up

We have an upcoming LBaaS v2→v3 CCM migration across 4 prod Kubernetes clusters. Each cluster gets S-OUT'd one at a time (all app pods scaled to 0) while the other 3 absorb its traffic at a boosted replica count, then it comes back and the next cluster goes down. We already have a script for this, `k8s2.py` — a click-based CLI with `backup`/`down`/`up`/`verify` commands and a little state machine (`discovered -> scaled_down -> restored`). I wanted to extend it to also handle the scale-*up* side properly instead of hand-waving it, and asked Claude to help design it. This is the story of how that spiraled and where I pulled the plug.

## The duplication that started it

First real finding: `k8s2.py` exists as three separate copies, one per migration folder (`20260728-exacc-migration`, `20260917-lbaas-migration`, `20260924-lbaas-migration`). They'd already drifted — the oldest copy is missing a `-c/--all` cluster-filtering flag the two newer ones have. Obvious next move: extract it to a shared `tools/` location so there's one copy and the drift stops.

Except — no. Each migration folder is a one-off, used once, then left as a historical record. Nobody re-runs `20260728`'s script, so it not having a feature added six weeks later isn't "drift," it's just... a snapshot of what existed when that migration ran. Forcing a shared abstraction across migrations that don't actually need to stay in sync buys nothing and adds a "which version is this pinned to" question that didn't exist before. Colocation + copy-forward-and-evolve is the right call here, git history is the version log. I killed the extraction idea entirely once I said this out loud.

## The targets file went through four shapes in one conversation

This is the part that should've been a five-minute decision and instead ate the whole session:

1. **One file with all 4 rounds nested inside, grouped by round.** Rejected — baking "round" into the schema means the tool has to know rounds exist, which is exactly the kind of migration-specific narrative that shouldn't live in code/schema.
2. **One flat file per round** (`round1.targets.json` ... `round4.targets.json`). Better — "round" becomes a filename, invisible to the tool.
3. **One folder per round** (`round1-jpe1-trv1-scaledown/`, etc.) so the folder name can say which cluster goes down that round.
4. **Drop the round number entirely** — the cluster name already tells you which round it is. `scaledown-jpe1-trv1/`, `scaledown-jpe1-trv2/`, etc. This is where it landed.

Each step was a real improvement and I don't regret any of them, but four iterations for "how do we name some JSON files" is a lot of iteration for something this small.

## The sequencing insight that actually mattered

The one genuinely good idea in the whole session: instead of scaling the 3 survivors up before *every* round and back down after, scale **everything** up to 133% capacity *once*, upfront, before round 1 even starts. Then every round is identical — target cluster goes `boosted → 0 → boosted` — and nothing else moves until a single final step brings all 4 clusters back to true baseline at the very end. This cuts total scaling operations roughly to a third of the naive "oscillate every round" version, and makes every round symmetric instead of round 1 being a special case.

## Reinventing Terraform badly, then less badly

I'd designed a standalone `verify-baseline` command — check live state against what a file expected, hard-abort on mismatch, before any destructive `down`/`up`. When I asked whether this was even a real pattern, turns out: yes, obviously — it's Terraform's stale-plan protection (`Error: Saved plan is stale`), and Kubernetes does the same thing with `resourceVersion`-gated conditional updates. But my standalone command was a clunky reinvention. The actual right shape is `plan` (read live state, diff against declared intent, write a reviewable plan file) / `apply` (re-check drift immediately before mutating, then execute) — the verify step falls out of the plan/apply split for free instead of being a separate thing you have to remember to run.

## Three agents argued about a YAML file's syntax

At this point I asked for three agents to independently propose a config file format: Terraform-HCL-style (named blocks, `variable` with descriptions), Kubernetes-CRD-style (`apiVersion`/`kind`/`metadata`/`spec`, label selectors), and a minimalist agent whose entire job was to argue the other two were overkill.

The minimalist won, and won cleanly. The original complaint — `scale_factor: 1.33` "isn't descriptive enough" — was never about *shape*. It didn't say what the factor multiplied or when it applied. Renaming it and adding one comment fixed 90% of the complaint with zero new nesting. The HCL-flavored proposal would've pulled in a `python-hcl2` dependency and implied a state/provider model that doesn't exist here. The CRD-flavored proposal implied a controller reconciling a live resource and invited someone to `kubectl apply -f` a file that is never meant to touch a cluster. Both added ceremony that answers questions nobody was asking.

## Then I caught a real bug on the second pass

After "locking" the minimal file, I pushed back that it still didn't describe *what the migration does* — the phase semantics (`scaleup-all`, `scaledown`, `restore`, `scaledown-all`) only existed in Python, not in the declarative file. Fair complaint, so phases came back into the YAML as named blocks with descriptions (this time in plain YAML, not HCL — no dependency, same descriptiveness).

Then, walking through "okay, how does this actually get *used*," I found the bug: `restore`'s target is "boosted," and if that's computed as `current_replicas * boosted_capacity`, it's wrong — at restore time, current is `0` (the cluster was just scaled down), so `0 * 1.33 = 0`, not the boosted number you actually want. "Boosted" and "baseline" only mean something relative to a snapshot taken once during `scaleup-all`, not something recomputable from live state at arbitrary later points. Needed a `baseline.json` written once by `scaleup-all`'s `apply` step, read by every later phase instead of re-derived.

That's a real correctness bug that would've silently scaled a restored cluster to 0 replicas during a real prod migration, caught only because I made myself trace the actual command sequence end to end instead of trusting the schema looked right.

## Where I landed: nowhere, on purpose

None of this shipped. It's a genuinely nicer design than what exists — but it's also a full rebuild of a script that already works, three days before the actual migration window. Better to ship the boring existing `backup`/`down`/`up`/`verify` flow for the real operation and revisit `plan`/`apply`/declarative-policy as a proper project later, not under time pressure with a maintenance window bearing down.

## Lessons, for future me

- **Duplication isn't automatically a bug.** Before "fix the drift," ask whether the copies are supposed to converge at all. One-off, used-once, historical artifacts don't need to.
- **A file complaint about "not descriptive enough" is usually a naming/comment problem, not a schema problem.** Try the cheap fix before reaching for more structure.
- **Borrowing a well-known shape (HCL blocks, K8s CRDs) has a real cost if the shape implies machinery you don't have** (a state backend, a reconciling controller). If the borrowed shape leads someone to a wrong mental model of what the file does, it's not free.
- **The best way to find a bug in a design is to trace the actual sequence of commands end to end with concrete values**, not to review the schema in the abstract. The baseline-snapshot bug was invisible in the YAML and obvious the moment I asked "okay, what does `restore` actually compute right now."
- **Multi-agent brainstorming is genuinely good for surfacing a spread of positions fast** (reusability vs. safety vs. YAGNI, or three syntax styles) — but the synthesis step still needs a real human decision. Three independent proposals converged on "the tool duplication is real, the schema debate is bikeshedding" faster than I would've gotten there alone.
- **Time-boxing matters more than getting the design right.** The right call here wasn't "finish the good design," it was "notice the design is good but not urgent, and ship the boring thing that already works."
